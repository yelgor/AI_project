# Інструкція користувача: конструктор приміщення та радіоекспериментів

## 1. Що можна робити

Побудувати приміщення зі стін і дверей, задати радіоматеріали, розмістити
передавач Tx і приймач Rx у 3D, додати офіційний Husky A200, керувати ним
і записувати результати Sionna RT. Користування редактором не потребує
ручного редагування JSON або знання ROS-команд.

У світі є один Tx, один Rx та один Husky. Rx може бути незалежним статичним
пристроєм або антеною, закріпленою на роботі. Gazebo симулює рух і зіткнення,
Sionna — радіопоширення. Робот у viewport використовує 6 official Clearpath
visual meshes; його фізична модель і контролери в Gazebo теж Clearpath.

## 2. Встановлення на іншій машині

Перевірений основний шлях — Linux x86_64. Потрібні:

- Python 3.12 з venv, системні LLVM та libatomic;
- Node.js 20.19+ або 22.12+, npm;
- Docker Engine та Compose v2, запущений Docker daemon і права доступу;
- кілька ГБ для пакетів ROS/Gazebo; рекомендовано щонайменше 20 ГБ вільного
  диска для першої збірки, більше для Docker `vfs` та великих датасетів;
- мережевий доступ до npm/PyPI/Docker Hub, ROS та Ubuntu/Debian пакетів.

На Ubuntu 24.04 Python prerequisites:

```bash
sudo apt update
sudo apt install python3-venv libllvm18 libatomic1
```

На Debian 13 використовуйте `libllvm19` замість `libllvm18`. ROS/Gazebo
працюють у контейнері Ubuntu 24.04, тому Ubuntu ROS-пакети на Debian хост
не встановлюйте. Node/Docker встановлюйте за їхніми офіційними інструкціями.

```bash
git clone https://github.com/yelgor/AI_project.git
cd AI_project
bash scripts/run_demo.sh
```

Це встановлює Python залежності, робить `npm ci` і збірку frontend,
збирає два Docker-образи та запускає сервіси. Перша інсталяція ROS може
тривати довго. Скрипт створює `.env` з LOCAL_UID/LOCAL_GID власника checkout,
якщо файл не існує; контейнери пишуть дані від цього користувача. Існуючий
`.env` не перезаписується — перевірте ці два поля для свого UID/GID. Скрипт повертається після старту контейнерів; кілька секунд
потрібно на ініціалізацію solver і підготовку visual assets.

У браузері відкрийте адресу `http://127.0.0.1:8010` на цій самій машині.
Це звичайний локальний інтерфейс застосунку, а не cloud preview.
Для хмарної машини потрібен дозволений port forwarding/SSH-тунель;
автоматичного браузерного доступу платформа onboarding не надає.
Сервіс не має авторизації та за замовчуванням прив'язаний до loopback.
Не відкривайте його у публічну мережу без окремого контролю доступу.

За корпоративного TLS-проксі:

```bash
RADIO_CA_BUNDLE=/path/to/trusted-ca-bundle.pem bash scripts/run_demo.sh
```

Передається довірений публічний CA bundle під час Docker build; перевірка
TLS не вимикається. Для npm/host Python теж має бути налаштована довіра
до цього проксі у середовищі. Це не місце для паролів чи API-токенів.

Якщо порт 8010 зайнятий:

```bash
RADIO_PORT=8020 docker compose up -d --no-build
```

Відкривайте той самий порт у браузері. Далі в прикладах default — 8010.

## 3. Початок роботи зі сценою

Ліва панель містить назву, шаблони й список об'єктів. Центральна — 3D viewport.
Права — властивості вибраного об'єкта, керування Husky та датасетами.

Оберіть шаблон:

- **Порожньо:** підлога, Tx/Rx, Husky; зручно для baseline;
- **Кімната:** 8×8 м, висота 3 м, двері шириною 1.6 м і висотою 2.2 м;
- **Коридор:** та сама зовнішня кімната з внутрішньою перегородкою і проходом.

Шаблон змінює чернетку редактора. Кнопка **Застосувати сцену** робить її
активною для solver та експорту Gazebo. Позначка **Є зміни** означає,
що ви бачите незастосовану чернетку. Вимірювання/збір за нею заблоковані.

Під час запущеного Husky або активного збору редагування сцени заблоковане.
Спершу завершіть запис/grid і зупиніть Husky, тоді редагуйте. Якщо Husky запущений, Apply
зупиняє стару симуляцію. Новий Run створить його у spawn нового сценарію.

## 4. Камера, вибір та редагування

| Дія | Керування |
| --- | --- |
| Орбіта камери | Ліва кнопка миші + рух |
| Панорама | Права кнопка + рух |
| Масштаб | Колесо |
| Вибір | Клік по об'єкту або його рядку в списку |
| Переміщення | «Переміщення», перетягнути стрілку X/Y/Z |
| Поворот | «Поворот», перетягнути кільце |
| Стандартний огляд | «Вся сцена» |
| План зверху | «Зверху» |
| Бачити робота за стінами | «Прозорі стіни» |

Прозорість стін і камери змінюють лише відображення. Вони не прибирають
перешкоди з фізики/радіосцени. Для стін і spawn робота підтримується yaw
навколо Z; для антен — yaw/pitch/roll. Точні значення вводяться справа.
Числові поля та gizmo змінюють одну чернетку.

Всі положення й розміри — метри. Z спрямована вгору. У UI кути у градусах,
у збереженому JSON — радіани. `center` об'єкта — його геометричний центр.

## 5. Як побудувати приміщення

1. Почніть із «Порожньо» або готової «Кімнати».
2. Натисніть **＋ Стіна**. Вкажіть центр, довжину X, товщину Y та висоту Z.
   Для стіни висотою 3 м на підлозі центр Z дорівнює 1.5 м.
3. Задайте yaw і позицію. Дублюйте стіни для протилежних сторін.
4. **＋ Дверна стіна** додає три сегменти з прорізом між ними.
   Для переміщення всієї дверної стіни перемістіть кожен сегмент: групування
   цих трьох об'єктів ще немає. Сегменти мають незалежні id.
5. Додайте перешкоди або опційну стелю; не видаляйте підлогу, якщо потрібен Husky.
6. Для кожного об'єкта оберіть ITU-матеріал і товщину радіошару.
7. Застосуйте сцену, перевірте вимірювання, збережіть сценарій JSON.

Кімната має бути простором **між** стінами. Великий суцільний box не створює
порожню будівлю: Rx усередині такого об'єкта буде відхилений.
Двері не анімовані; проріз фізично відкритий у Sionna та Gazebo.
Довільні CAD/mesh-будівлі та групове редагування поки не підтримуються.

## 6. Tx і Rx у 3D

Оберіть **Передавач** або **Приймач** у списку; задайте X/Y/Z і орієнтацію.
Позиція не може бути всередині solid стіни; Tx і Rx мають бути не ближче 0.1 м.
У статичному режимі натисніть **Виміряти у приймачі**. Нижні картки покажуть
RSSI, SNR та число шляхів; повний CIR/затримки — у деталях справа.

Для перевірки третьої координати змініть лише Rx.Z, застосуйте сцену та
виміряйте знову. У результаті `position_m[2]` має відповідати введеному Z.
Зміна координат не гарантує монотонної зміни RSSI: можливі інтерференційні
максимуми/мінімуми. Якщо шляхів не знайдено, RSSI/SNR будуть `null`.

Радіопанель задає частоту, потужність Tx, bandwidth, noise figure, період
запису, seed та бюджет трасування. Частота/bandwidth у UI — MHz,
у сценарії — Hz. Великі budget/max_depth збільшують час обчислення.

## 7. Husky та антена на роботі

1. Виберіть **Husky A200** й задайте spawn X/Y/Z/yaw у вільному місці.
   Стандартний spawn Z=0.3 м; робот опуститься на підлогу за фізикою Gazebo.
2. У властивостях **Приймача** оберіть **Антена на Husky**.
3. Задайте mount X/Y/Z відносно base_link. Стандартне `[0,0,1]` —
   точка на 1 м вище origin base_link, а не гарантовано 1 м над землею.
4. Застосуйте сцену, натисніть **Запустити Husky**, дочекайтесь `running`.
5. Утримуйте WASD/стрілки або кнопки руху. Клавіші руху не активні під час
   введення тексту/чисел у поля. Відпускання/втрата фокуса припиняє команди;
   runtime має deadman 0.5 с. Space або центральна ■ зупиняє рух.
6. **Завершити** зупиняє процеси симуляції. Це також завершує активний запис.

Поза робота у viewport та антена отримуються з фактичної world pose Gazebo.
Повний quaternion робота перетворює mount, включно з поворотом/нахилом.
Корпус робота не доданий до радіогеометрії, visual-колеса у браузері
не анімовані; у Gazebo колеса й контролери фізично працюють.

Стани: `stopped` — не запущений; `starting` — запускається;
`running` — надходить актуальна world pose; `pose-stale` — поза не оновлюється.
Останній стан не слід вважати готовим каналом: перевірте логи й перезапустіть.
У режимі static рух Husky не переносить незалежний Rx.

## 8. Збереження та передача

**Зберегти сценарій** завантажує поточну чернетку JSON. **Відкрити JSON**
валідує файл і завантажує його в редактор; для активації потрібен Apply.
Legacy `config/world.json` також підтримується через migration у scene v2.

Активний сценарій і датасети зберігаються у `.runtime/`, який ігнорує Git.
Перед передачею іншій людині збережіть JSON і ZIP потрібних датасетів;
один Git push ці локальні дані не переносить. `docker compose down` не
видаляє їх, бо вони лежать у checkout bind mount.

## 9. Діагностика та завершення

```bash
docker compose ps
docker compose logs --tail 100 radio husky
tail -n 100 .runtime/husky.log
```

Для ROS:

```bash
docker compose exec husky bash
source /opt/ros/jazzy/setup.bash
ros2 topic list
ros2 topic echo /radio/measurement std_msgs/msg/String
```

Після закриття браузера компоненти можуть залишатися запущеними.
Спершу завершіть запис/робот у UI, потім `docker compose down`.
Після нового старту активна сцена відновлюється, але Run робота потрібно повторити.
Незавершені записи після аварійного перезапуску позначаються `interrupted`.

Якщо official visual assets недоступні, UI показує габаритну рамку й повідомлення,
а не підміняє Husky іншою моделлю. Перевірте startup husky service та
`scripts/prepare_husky_assets.py`. WebGL потребує сучасного браузера.
Повний набір troubleshooting — у [TECHNICAL.md](TECHNICAL.md).
Для роботи з даними — [DATASET_GUIDE.md](DATASET_GUIDE.md).

Автономні цілі Nav2, відновлення RSSI, B0/B1/IDW/GPR, часові карти та
демонстрація тепер доступні на окремій сторінці **Експерименти / Replay**.
Порядок оновлення Docker і керування — [EXPERIMENT_GUIDE.md](EXPERIMENT_GUIDE.md).
