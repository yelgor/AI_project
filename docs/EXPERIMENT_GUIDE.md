# Автономні експерименти: запуск, карти, навчання і демонстрація

Система використовує готові Gazebo/Clearpath для фізики, Nav2 для руху,
Sionna RT для каналу і scikit-learn для GPR. Власні модулі з’єднують ці
компоненти, ведуть журнал і обирають ціль відновлення зв’язку.

## Оновлення інсталяції

Після отримання цього оновлення потрібна **перебудова Docker images**:
додані Nav2 packages і scikit-learn. Старі images цих залежностей не мають.
Перед оновленням завершити власний активний запис/експеримент і зберегти JSON/ZIP.

```bash
git pull --ff-only
bash scripts/run_demo.sh
```

Відкрити `http://127.0.0.1:8010/experiments.html` або посилання
**Експерименти / Replay** у верхній панелі конструктора.
Потрібні ті самі Python/LLVM, Node.js і Docker prerequisites, що в USER_GUIDE.
На вже перебудованій інсталяції достатньо `docker compose up -d --no-build`.

## Перша демонстрація

1. Натиснути **Підготувати демо відновлення**. Це застосує кімнату, антену
   Husky, маршрут до точки за дверима та приклад порога RSSI.
2. Дочекатися `Husky: running · Nav2: ready`. `running` без `Nav2: ready`
   ще не означає готовності автономного планувальника.
3. Натиснути **Почати експеримент**. Метод B1 буде отримувати вимірювання,
   робот рушить за маршрутом огляду, після підтвердженої деградації обере
   відвідану хорошу точку й поїде до неї через Nav2.
4. Перемикати шари карти. Помаранчева точка — Tx, синя — Husky,
   кольорові точки — вимірювання, темна лінія — траєкторія,
   помаранчева лінія — запланований маршрут. Колір RSSI має фіксовану шкалу.
5. Дочекатися `RECOVERED_WAIT` або подивитися причину `FAILED`.
   Відновлення може потребувати кількох цілей через локальні зміни RSSI
   й допуск досягнення цілі Nav2. Немає гарантії успіху кожного методу.
6. Вибрати запуск праворуч, натиснути **Відтворити**, пересувати часовий
   slider або ввімкнути **Replay**. Карта/маршрут/ціль відповідають вибраному часу.
7. Завантажити **ZIP експерименту**. Логи лишаються в `.runtime/experiments/`.

Це повністю автономний **survey → degradation → recovery** приклад.
Для демонстрації саме **телеоперація → втрата → автономне відновлення**
залишити поле маршруту `[]`, розпочати експеримент і вести робот
WASD/екранними кнопками. Монітор спрацює за тим самим критерієм, а після
переходу в recovery ненульові ручні команди відхиляються.

**Space/■** скасовує автономний рух; **Зупинити все** завершує Gazebo.
**Завершити** завершує експеримент і утримує робот на місці.
**Повернути ручне керування** явно скасовує автономність та повертає teleop.
Після `RECOVERED_WAIT` керування не повертається оператору автоматично.
Закриття вкладки не зупиняє експеримент; його виконує backend.

## Довільні світи та окрема перевірка навігації

Шаблони: порожня сцена, кімната з дверима, коридор із проходом,
склад зі стелажами, двір із будівлями. Два останні також доступні в конструкторі.
Редагувати геометрію/матеріали/Tx у конструкторі, зберігати JSON і застосовувати
сцену перед запуском. Під час експерименту сцена незмінна.

На сторінці експериментів клік по карті задає XY цілі. Вказати yaw у градусах,
натиснути **Їхати через Nav2**. До початку радіоексперименту це дає окрему
перевірку маршруту/об’їзду. Ціль усередині перешкоди або недосяжна ціль
повинна повернути помилку. Обраний Nav2 маршрут проходить по occupancy,
експортованій із тієї самої геометрії, що й Sionna/Gazebo.

Планувальник — upstream NavFn з A*, контролер — Regulated Pure Pursuit.
Конфігурація: `config/nav2.yaml`. Використовується консервативний круговий
footprint радіуса 0.55 м та inflation 0.7 м; це може відхилити фізично
прохідний вузький прохід. Проріз коридору розширений для цього footprint.
Нові світи створюйте з достатнім запасом, перевіряючи проходи реальним проїздом.

Локалізація — **ground truth Gazebo**, не SLAM/AMCL. Runtime обчислює
map→odom із world pose й odometry; upstream Clearpath дає odom→base_link.
TF і Nav2 працюють у namespace `a200_0000`, координати map відповідають world.
Поки що підтримані статичні перешкоди та плоска місцевість. Карта зі статичної
геометрії не підміняє сенсори для об’їзду динамічних об’єктів.

## Режими та критерій зв’язку

`TELEOP` — ручне керування; `SURVEY` — заданий автономний маршрут огляду.
Після поганих вимірювань протягом `degraded_s`:
`LINK_DEGRADED → RECOVERY → RECOVERED_WAIT`.
`FAILED` — немає безпечної досяжної цілі, timeout, stale input або помилка Nav2.
`CANCELLED` — оператор завершив запуск або маршрут закінчився без деградації.
`INTERRUPTED` — backend було перезапущено.

Поганий сигнал: `RSSI < q_safe_dbm − hysteresis_db`; хороший для відновлення:
`RSSI >= q_safe_dbm`. Для успіху потрібна послідовність хороших вимірювань,
що охоплює `stable_s`. Періоди підтвердження й timeout вимірюються sim-time.
Є також wall-clock timeout для завислої симуляції.
No-path RSSI=null вважається поганим synthetic signal; помилки розв’язувача
не перетворюються на виміряний RSSI. Застарілий радіопотік або поза завершують
експеримент із помилкою. За відсутності зв’язку з radio backend runtime
скасовує автономний рух через watchdog.

Це **RSSI proxy відновлення**, а не отримання пакетів модемом. Пакетний PHY,
втрати пакетів, protocol latency, фізичний receiver noise і RF-корпус Husky
не додані. Параметр noise_db у GPR — припущення регресії, а не шум Sionna.

## Методи та навчання

| Метод | Як обирає ціль |
| --- | --- |
| B0 | Остання виміряна хороша позиція робота |
| B1 | Хороша відвідана позиція з найкоротшим валідним Nav2-шляхом |
| IDW | Клітинка з інтерпольованим RSSI >= порога та найкоротшим Nav2-шляхом |
| GPR-zero | Нульове середнє, ядро Matérn 3/2; відбір за μ−βσ |
| GPR-pathloss | Лог-відстаневе середнє, Matérn 3/2 для залишків; відбір за μ−βσ |

Усі кандидати перевіряються справжнім ComputePathToPose. Евклідова відстань
служить лише нижньою межею для припинення пошуку, коли коротшого шляху вже
бути не може. B0 припиняє спробу, якщо його остання хороша точка недосяжна.
При невдалому/завершеному без відновлення під’їзді ціль виключається й метод
обирає наступну; це логуються як replans. Якщо кандидатів немає — FAILED і stop.

GPR навчається онлайн лише на вже отриманих скінченних RSSI: до 150 останніх
просторово різних точок із мінімальною відстанню 0.15 м. Повна історія
зберігається в журналі. Для log-distance mean коефіцієнти оцінюються на цих
самих точках; при недостатньому діапазоні відстаней використовується їх середнє.
За замовчуванням kernel amplitude=1600 dB², length scale=2 м, noise_db=2 dB.
Прапорець оптимізації вмикає fit kernel hyperparameters через scikit-learn.
Для порівняння всі параметри слід зафіксувати після validation.

σ — latent standard deviation GPR. Додатне β штрафує невизначеність;
β=0 використовує тільки μ. IDW не має каліброваної σ, тому β для нього
відхиляється. Для B0/B1 IDW-карта використовується **лише для візуалізації**,
а рішення беруться з історії вимірювань. Nav2 не навчається нейромережею.

Карта — горизонтальний зріз на поточній висоті антени з кандидатами позицій
бази та поточним yaw. Монтажний offset враховується при прогнозі RSSI,
маршрут перевіряється для бази. Для сильних нахилів/неплоскої місцевості
цей 2D Nav2 експеримент не призначений.

## Серії запусків

`config/experiments/pilot.json` задає 5 світів × 2 положення Tx. Це пілотні
пороги/маршрути; вони потребують перевірки, а не гарантують втрату/відновлення
в кожній сцені. Власний JSON має `trials` з name/world/route/config; можна
передати повний scene замість шаблону, tx/spawn/yaw_rad та split.

Швидкий запуск однієї умови:

```bash
python3 scripts/run_experiments.py --world room-a --methods B1 --output .runtime/reports/room
```

Повна серія (тривала; 70 запусків на один повтор):

```bash
python3 scripts/run_experiments.py --repeats 3 --betas 0 1 --output .runtime/reports/full
```

Runner замінює активну сцену, запускає/зупиняє Gazebo для кожного trial,
зберігає ZIP, trials.csv і report.json, включно з невдачами. Не запускати
паралельно з власним збором даних або іншим runner. Повторний запуск у ту
саму output-directory перезаписує звіт; для нової серії задавати іншу папку.

Прості повтори маршруту не гарантують ідентичної історії до втрати: частота
надходження Sionna залежить від wall-clock навантаження. Для чистої β-абляції
потрібен спільний checkpoint та **однакова causal history**:

```bash
python3 scripts/run_experiments.py --history-from ID_ЗАПУСКУ \
  --methods B0 B1 IDW GPR-zero GPR-pathloss --betas 0 1 \
  --output .runtime/reports/paired
```

Замість ID_ЗАПУСКУ підставити ідентифікатор завершеного запуску зі справжньою
деградацією. Runner бере перший LINK_DEGRADED, переносить Husky в ту саму
XY-позицію/yaw і передає кожному методу тільки вимірювання до цієї події.
Спостереження після втрати з джерела виключені. Перша модель/ціль
використовує тільки спільний префікс; нові online-вимірювання записуються,
але допускаються до моделі після першої цілі. Фізичні швидкості/стан
контролера не відновлюються з Gazebo snapshot: кожен метод починає recovery
зі спокою, з однаковим spawn і history. Це парне порівняння recovery зі спокою.
Після старту нові вимірювання визначаються власною реальною траєкторією методу.

Звіт має частку успіхів та Wilson 95%, усі статуси, а також різниці часу/шляху
для пар, де обидва методи успішні, з bootstrap 95%. При n=1 інтервал
вироджується й не є свідченням статистичної переваги. Явне повернення керування
оператору/скасування фіксується як operator_interventions. Contact-sensor
для зіткнень не підключений: статуси, відміни й помилки
треба читати разом із метриками. Не називати відсутність помилки доказом
нульових зіткнень. Успішний «контроль без втрати» не є recovery-success.

## Reference-карта та оцінка прогнозу

Завершити експеримент, зупинити Husky, не змінювати геометрію/Tx/radio settings.
У конструкторі зібрати grid на висоті антени (приблизно 0.83 м для mount z=0.7
на плоскій сцені). Кількість точок до 2500, кількість клітинок прогнозу до 900.
Інша висота — інший зріз. Reference доступний лише viewer/evaluation, не
радіометоду; він ніколи не підмішується до online training.

На сторінці експериментів вибрати завершений запуск і grid-датасет,
натиснути **Показати reference**. Перевіряється RF field hash і висота;
spawn робота може відрізнятися, адже його корпус не входить у RF-геометрію.

Порівняти IDW/GPR на **однаковому** часовому префіксі:

```bash
.venv/bin/python scripts/evaluate_radio_maps.py ШЛЯХ_ДО_EXPERIMENT_ZIP ШЛЯХ_ДО_GRID_ZIP \
  --at 15 --min-distance 1 --output .runtime/reports/maps.csv
```

`--at` — абсолютний sim-time зі slider; тут 15 є прикладом, оберіть час
свого запуску. Скрипт враховує час готовності вимірювання, виключає reference
точки ближче min-distance в XY до **всіх** доступних спостережень і відхиляє
інше RF field/невідповідну висоту. Видає MAE/RMSE, а для GPR — NLPD і coverage
95% з observation noise. Це spatial holdout конкретної сцени; для заяви про
перенесення потрібні окремі test-світи/сесії. β не змінює якість μ/σ при
однаковій історії, він змінює відбір цілей.

Послідовно, без активного власного запису:

```bash

python3 scripts/check_navigation_experiments.py
npm --prefix frontend run test:e2e
```

відхиляє solid goal, скасовує рух і перевіряє зупинку, запускає B1 recovery
та перевіряє timeline/ZIP/hold.
Browser check використовує цей завершений запуск для перевірки replay.
Старі `check_api.py` і `check_constructor_integration.py` лишилися доступні.

```bash
docker compose logs --tail=100 radio husky
tail -n 150 .runtime/husky.log
```

Nav2 ready=false: перевірити активування lifecycle nodes, map/odom/base_link
TF, packages у новому image, clock і footprint. Відсутній joystick `/dev/input/ps4`
не заважає браузерному керуванню. Нульові команди після blur/release не
скасовують Nav2; явні Space/Stop/повернення teleop скасовують action.

## Native-процес і точність доїзду

Під час перевірок Dr.Jit 1.5/LLVM спостерігалися compiler abort і segfault
при повторному використанні сцен. Кожна сцена тепер належить окремому
процесу, між ним і backend передаються тільки координати/звичайні дані.
Заміна сцени завершує її процес і створює новий. Збій native-коду
повертає помилку; експеримент зупиняє рух і завершується FAILED, а HTTP/UI
лишаються доступними. Для повторного запуску потрібно застосувати сцену.
Штатний JitFlag.MergeFunctions лишено увімкненим: вимикання цієї оптимізації
виявилося ненадійним на floor-only сцені. solver_runtime записує налаштування;
у ранніх пілотних архівах вони можуть відрізнятися.

Для single-process дебагу одного положення лишився upstream CLI:

```bash
.venv/bin/python app/radio.py --config config/empty.json sample 2 2 2
```

Для RF-задачі xy_goal_tolerance Nav2 зменшено до 0.03 м, yaw — до
0.05 rad; goal checker перевіряє XY і під час завершення повороту.
Перші пілоти використовували 0.2 м: цей допуск завеликий щодо масштабу
швидкого multipath fading на 2.4 GHz, тому повторні RSSI можуть відрізнятися.
Налаштовуйте tolerance на validation та проводьте нову серію після
перезапуску Husky. Нові manifests зберігають YAML; ранні пілоти використовували
[navigation.yaml](../examples/experiments/navigation.yaml).
