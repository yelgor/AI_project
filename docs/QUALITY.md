# Якість експериментів, масштабування й ітерації

## Протокол перед збором

Спочатку проєктуємо експеримент, потім запускаємо серію. П’ять сімейств світів:
будівля, офіс із кімнатами, склад зі стелажами, квартал і двір. Для кожного є дві
позиції Tx та окрема ціль у радіотіні. Спільний scene JSON породжує Gazebo-геометрію,
Nav2 occupancy та Sionna-сцену. Джерело — `app/missions.py`;
повні конфігурації — `config/experiments/missions.json`.

```bash
.venv/bin/python scripts/validate_missions.py
```

Перевіряються реальні Sionna-покази в цілі й сусідніх позиціях ±0.15m, геометричне
перекриття прямої видимості, clearance Husky та запас нижче порога. Артефакт:
`.runtime/reports/mission-preflight.json`. Така сама перевірка виконується сервером
перед місією. Вона не навчає контролер. Сигнал не підміняється правилом LOS/NLOS:
рефракція, дифракція й відбиття залишаються upstream Sionna RT.

## Два різні протоколи

**Повні місії (`full`)**: кожного разу фізичний проїзд від бази до заданої радіотіні,
підтвердження втрати, автономне повернення. Вихідна історія між проїздами може
відрізнятися через дискретизацію часу та рух.

**Парні повернення (`paired`)**: спочатку для кожної умови виконується повна фізична
місія. Зберігаються поза першої підтвердженої втрати в цільовій зоні та тільки
вимірювання, доступні до неї. Кожен метод фізично стартує повернення з цієї пози/heading
у Gazebo, зі спільною історією до втрати. Перше рішення використовує точно цей
префікс; нові вимірювання надалі дозволені. Дані після втрати з вихідної місії
не потрапляють до seed. Це N реальних повернень плюс окремі вихідні місії,
а не N повних виїздів від бази. Швидкість у checkpoint скидається: всі методи
починають з однакового спокою; simulation clock та odometry не скидаються.

Згладжування виконується в лінійній потужності за **часом фізичного вимірювання**,
а не за одночасним часом завантаження seed. Інакше сильні початкові покази можуть
помилково виглядати як відновлення зв’язку в радіотіні.

## Серія від 100 епізодів

Вкладка **Серія експериментів** дозволяє обрати кількість, методи, full/paired
і 1–4 воркери. Для всіх методів повний набір одного повтору:
10 умов × [B0, B1, IDW, GPR-zero β0/β1, GPR-pathloss β0/β1] = **70 епізодів**.
Для двох повних повторів оберіть **140**. Рівно 100 також підтримується, але це
частково заповнена факторна таблиця: порівнюйте лише наявні спільні пари.

```bash
python3 scripts/run_experiments.py --runs 140 --workers 2 --protocol paired \
  --output .runtime/reports/benchmark
```

Для повних виїздів замініть `paired` на `full`. На 4–8 CPU почніть із двох воркерів;
зайві воркери можуть сповільнити Gazebo та збільшити пропуски вимірювань. Кожен
має власні ROS domain, Gazebo partition, HTTP ports, runtime/логи та процес Sionna.
Додаткові багатогігабайтні Docker images на кожен воркер не створюються.

Між епізодами тієї самої геометрії зберігається прогрітий Gazebo/Nav2: реальна
поза Husky скидається через GZ service; епоха/ревізія відкидає стару телеметрію.
Sionna worker зберігається для однакового RF-поля. Зміна Tx перезавантажує RF-поле,
зміна геометрії — також фізичний світ. DrJit cache спільний на диску. CPU threads
обмежені на воркер. Вимкнення збереження CIR прибирає великий Python/JSON payload,
але RSSI все одно обчислюється за всіма трасованими комплексними коефіцієнтами.

Поточний прогрес і всі невдачі записуються на диск. Зупиніть серію кнопкою або
Ctrl+C у CLI. Продовження незавершених індексів:

```bash
python3 scripts/run_experiments.py --resume CAMPAIGN_ID --output .runtime/reports/benchmark
```

У UI введіть ID у полі **Перервана серія → Продовжити серію**.
Завершені індекси зберігаються; невдалі завершені спроби не підміняються новими.
Для повторної перевірки після виправлення запускайте нову серію з новим ID.

## Що рахуємо

Основний показник — **частка успішних відновлень серед усіх запланованих спроб**,
включно з setup, navigation і radio failures. Окремо — частка успіху серед епізодів,
у яких втрату було підтверджено. Зберігаються причини всіх невдач.

- Час повернення: t стабільного відновлення − t підтвердженої втрати, simulation s.
- Довжина повернення: сума відстаней між world poses під час recovery.
- Близькість: відстань кінцевої антени до найближчої відомої доброї точки до втрати.
- Path stretch: довжина повернення / пряма відстань між початковою й кінцевою позою.
  Це діагностика звивистості, не відношення до невідомого оптимального безпечного шляху.
- RSSI-прогноз: MAE, RMSE, bias, false-safe fraction; для GPR — NLPD та coverage95
  з observation noise. Оцінка розбита за відстанню до найближчого навчального показу.
- Підготовка: cold/warm, час readiness, reuse RF. Окремо solver wall time та кількість
  нових показів. Повторені seed-покази не рахуються як нові вимірювання.
- Перевірка зайнятої геометрії за позами: діагностичний круг 0.35m. Це не contact sensor.

Автоматичний `analysis/analysis.json` та CSV входять до ZIP серії. Повторний аналіз:

```bash
.venv/bin/python scripts/analyze_campaign.py .runtime/campaigns/CAMPAIGN_ID
```

Wilson95 у звітах описує епізоди; повтори в одному RF-полі й зі спільною історією
залежні. 140 повторів у 10 полях не є 140 незалежними світами. Додатково дивіться
macro-average по сценах, найгірший світ і paired differences тільки на спільних
умовах. Bootstrap для часу/шляху включає тільки пари з двома успіхами;
такий результат завжди треба читати разом із часткою невдач.

## Просторова перевірка та захист від витоку

Causal forecast оцінює наступні покази, навчаючись лише на результатах, доступних
до фізичного часу тестової пози. Точки тієї самої траєкторії корельовані.
Для перевірки карти в нових областях збирайте **окрему reference grid**, яку
контролер ніколи не отримує. Вона повинна мати однаковий field hash і висоту Rx.

```bash
python3 scripts/collect_reference.py --bounds -7 -6 7 6 --height .83228 --step .5
.venv/bin/python scripts/evaluate_radio_maps.py EXPERIMENT_ZIP REFERENCE_ZIP \
  --at LOSS_SIM_TIME --min-distance 1 --output .runtime/reports/holdout.csv
```

Перед reference grid зупиніть Husky, залишивши потрібну сцену активною.
`--min-distance` відсікає точки поруч із **будь-яким** відомим показом, включно
з тими, які відкинув 150-point training cap. Немає random-row split тієї самої
траєкторії. train: shadow/office/warehouse; validation: district; test: courtyard.
Налаштовуйте гіперпараметри лише на train/validation; після перегляду test він
стає дослідженим benchmark, тож для наступного твердження про узагальнення
потрібні нові геометрії та зафіксована до запуску конфігурація.

## Ітеративне ускладнення

Автоматичне розширення всіх полів серії незалежними grid-картами на трьох висотах:

```bash
.venv/bin/python scripts/expand_reference.py .runtime/campaigns/CAMPAIGN_ID \
  --step 1 --heights .83228 1.2 1.8
.venv/bin/python scripts/study_reference.py .runtime/campaigns/CAMPAIGN_ID
.venv/bin/python scripts/plot_campaign.py \
  .runtime/campaigns/CAMPAIGN_ID/analysis/analysis.json
```

Ці скрипти не під’єднують reference до контролера. ZIP містять CSV/JSONL,
сцену, field hash та `evaluation_only=true`. Для scoring використовуються
тільки позиції на висоті антени й принаймні за метр від усіх доступних показів.
Три висоти reference — статичні розрахунки Sionna, не додаткові фізичні заїзди.

`study_reference.py` порівнює noise_db=2/4/8 та fit kernel hyperparameters.
Два профілі обираються на train-сімействах, фінальний — на validation,
після чого test оцінюється один раз для кожного методу. Зберігаються
`reference-study/study.json`, `scores.csv`, `recommended-config.json`.
Емпірична β95 оцінюється лише на validation; це не гарантія безпеки в новому світі.
Рекомендовані параметри не застосовуються заднім числом до фізичної серії.
Щоб перевірити їх у русі, перенесіть noise_db/optimize_gpr/β у config нової
зафіксованої серії й порівняйте всі її успіхи/невдачі з baseline.

1. Перевірити deliberate shadow, clearance й успішний контрольний B1 проїзд.
2. Заморозити конфігурації, seed, версії та поділ світів; зібрати повну факторну серію.
3. Перевірити всі помилки, найгірші сцени, похибку за відстанню та false-safe рішення.
4. Виправляти підтверджену причину на train/validation. Старі звіти зберігати.
5. Додати нову геометрію: поворот будівель, вузькі проїзди з достатнім clearance,
   більше кімнат/матеріалів, інший Tx. Спершу знову перевірити фізичну радіотінь.
6. Зібрати нову серію та незалежну reference grid. Порівнювати всі результати.

Демонстраційний бар’єр якості: один запуск готує все потрібне, видно справжній
рух Husky з Rx, зрозуміло показані фаза/поріг/помилка, Stop працює, replay не
плутається з live, ZIP відтворює дослід. Кількість рядків не замінює цих перевірок.

Межі: synthetic narrowband RSSI, статичні перешкоди, Gazebo ground-truth localization.
Немає packet/modem PHY, SLAM або реальної апаратної перевірки. Навчаються online
карти IDW/GPR; reinforcement learning policy цим кодом не тренується.
